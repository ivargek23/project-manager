### Security – PR #60
- SecurityFilterChain with form login on a custom login page, logout and BCrypt password hashing
- Users loaded from the database through AppUserDetailsService and AppUserPrincipal
- Three roles with different capabilities: ADMIN, PROJECT_LEAD, MEMBER, described in the permission matrix
- Thymeleaf security dialect hides what a user may not do; 403 page; login and error messages in Croatian and English
- CSRF protection is on for all screens

### Method-level authorization – PR #63
- ProjectAccess bean with isLead, isMember and isAssignee checks for one project
- @PreAuthorize on the service methods of ProjectService and TaskService, so the screens and the REST API share the same rules
- The assignee check also takes the project id, so a task from another project can't pass it
- Non-admins only see projects they lead or are members of
- A project lead always becomes the lead of a project they create; only an admin can choose or change the lead
- Separate status update, allowed for the lead and the task's assignee, so members can move their own tasks without full edit rights
- PermissionMatrixTest reads the permission matrix from a CSV file (21 cases) and runs each one against PostgreSQL in Testcontainers, expecting success or 403
- ProjectAccessTest unit-tests the access checks

### REST API – PR #64
- Resources: /api/projects, /api/projects/{projectId}/tasks, /api/projects/{projectId}/tasks/{taskId}/subtasks
- DTO records for requests and responses, mapped with MapStruct; entities never leave the API
- Pagination and sorting on the project and task lists, with a whitelist of sortable fields and a maximum page size of 100
- Status codes: 201 with Location on create, 204 on delete, 400 for validation, 403, 404, 409 for a stale version, 422 for business rules (invalid lead, assignee outside the project)
- All errors as ProblemDetail from one @RestControllerAdvice limited to the REST controllers; validation errors list the invalid fields
- The API has its own stateless security chain with HTTP Basic. It ignores the session cookie and does not send a Basic challenge, so the browser never sends credentials on its own. Because of that CSRF is turned off only for /api/** and stays on for the screens. ApiSecurityTest proves both: a logged-in browser session gets 401 on the API, and a screen POST without a CSRF token gets 403
- @WebMvcTest tests for all three API controllers, covering success, 400, 403, 404, 409 and 422

### OpenAPI documentation – PR #65
- springdoc-openapi 3.2.0 with Swagger UI, limited to /api/**
- HTTP Basic security scheme, so the Authorize button works with the demo accounts from the README
- Every endpoint documents the error codes it can actually return, with the ProblemDetail schema
- Descriptions and examples on all request and response DTOs
- OpenApiDocsTest checks that the documentation is public, covers the API and leaves out the screens

### In progress: dependency editor with cycle check (#27)

Done so far:

- Recursive SQL query (WITH RECURSIVE) that checks whether the new link would close a loop and returns only true or false
- Second query that returns the loop as task titles, run only when a cycle is found, so the user sees why the link was rejected
- The project row is locked (PESSIMISTIC_WRITE) before the check, so two users can't create a cycle at the same moment
- Flyway V3 adds project.schedule_version, which every dependency change increases for the critical path cache
